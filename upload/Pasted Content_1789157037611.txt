3. CRITICAL BUG: COWRIE LOG VOLUME MISMATCH
============================================================

Inspect:

iot-honeypot-ids/pi/docker-compose.yml
iot-honeypot-ids/pi/honeypots/cowrie/cowrie.cfg
iot-honeypot-ids/pi/filebeat/filebeat.yml

Current Cowrie configuration says:

json_log_file = /var/log/cowrie/cowrie.json

But the Cowrie service mounts:

cowrie_var:/cowrie/cowrie-git/var

Filebeat mounts the same named volume as:

cowrie_var:/var/log/cowrie:ro

This does NOT guarantee that:

/var/log/cowrie/cowrie.json

inside Cowrie is the same filesystem location that Filebeat reads.

The current configuration can therefore produce:

Cowrie writes:
container filesystem /var/log/cowrie/cowrie.json

Filebeat reads:
named volume /var/log/cowrie/cowrie.json

while the named volume is actually mounted into Cowrie at:

/cowrie/cowrie-git/var

Fix the volume/path contract.

Choose ONE clear architecture.

Preferred:

Make the named Cowrie volume contain exactly the directory that
Filebeat reads.

For example, if Cowrie genuinely writes:

/var/log/cowrie/cowrie.json

then mount:

cowrie_var:/var/log/cowrie

inside Cowrie.

Do not simultaneously rely on an unrelated
/cowrie/cowrie-git/var mount for that log file.

Preserve whatever other Cowrie directories are actually required,
but make the JSON log path unambiguous.

Then Filebeat:

cowrie_var:/var/log/cowrie:ro

must see the exact same file.

Verify:

inside Cowrie:
 /var/log/cowrie/cowrie.json

inside Filebeat:
 /var/log/cowrie/cowrie.json

must refer to the same persisted volume data.

Do NOT solve this with a second copied log file.

Do NOT use host bind mounts unnecessarily.
