@Superpowers

You are working on my IoT Honeypot + Hybrid Intrusion Detection System research project.

PROJECT GOAL
============
Build a scientifically defensible, reproducible IoT intrusion-detection platform consisting of:

Computer 1: Raspberry Pi
- Runs IoT honeypots
- Generates/collects telemetry
- Runs Filebeat
- Sends telemetry to Computer 2

Computer 2: Fedora analysis server
- Elasticsearch
- Logstash
- Kibana
- Feature extraction
- Rule engine
- Supervised ML classifier
- Unsupervised anomaly detector
- Hybrid/fusion decision layer
- Research evaluation
- Experiment tracking

Computer 3:
- Future attacker/test machine
- Can temporarily be replaced by Android/Termux for controlled testing

IMPORTANT RESEARCH PRINCIPLE
============================
This is not merely a software demo.

The project must produce evidence that can survive technical scrutiny.

Therefore:

Never fabricate metrics.

GLOBAL EXECUTION RULES
============================================================

1. Work incrementally.

2. Before changing architecture, inspect the existing implementation.

3. Do not perform a giant rewrite.

4. Preserve working functionality unless there is a documented reason to change it.

5. Before modifying a subsystem:
   - inspect the relevant files
   - explain the current behavior
   - identify the defect
   - propose the smallest safe change

6. Every phase must have:
   - objective
   - implementation
   - tests
   - verification
   - artifacts
   - explicit PASS / FAIL / SKIPPED status

7. If a phase fails an important scientific-validity condition:
   STOP progressing to later research phases.

8. Existing invalid experiments must NOT simply be deleted.
   Preserve them as historical artifacts and mark them:
   INVALID / QUARANTINED / NOT VALID FOR EVIDENCE

9. Do not silently change historical metrics.

10. Every experiment must record:
    - experiment ID
    - dataset version
    - feature version
    - code version / commit
    - random seed
    - algorithm
    - hyperparameters
    - split protocol
    - train sample count
    - test sample count
    - label source
    - feature provenance
    - timestamp
    - notes
    - validity status

11. Use deterministic random seeds where applicable.

12. Add automated assertions for scientific validity.

13. Distinguish:
    - synthetic development data
    - controlled lab data
    - real uncontrolled telemetry
    - external public datasets

14. Do not use the word "zero-day" unless the experiment actually establishes a defensible definition of previously unseen behavior. Prefer:
    "previously unseen attack behavior"
    when appropriate.

15. Distinguish offline full-session classification from online/partial-session detection.

16. If a feature requires future events in a session, it cannot be presented as an online early-detection feature.

17. Never silently convert:
    no detection
    ->
    benign

18. Unknown/unlabeled data must remain UNKNOWN until independently labeled.

PHASE A: EXPERIMENT VALIDITY

PRIMARY OBJECTIVE
=================
Fix the invalid train/evaluate architecture.

Current conceptual problem:

dataset
 -> train on all rows
 -> split
 -> evaluate

This is invalid.

Required architecture:

dataset
 -> validate
 -> split
 -> fit preprocessing on TRAIN only
 -> train on TRAIN only
 -> freeze model
 -> evaluate TEST only
 -> record metrics

Implement a proper experiment runner.

Example conceptual interface:

run_experiment(
    dataset,
    split_protocol,
    algorithm,
    feature_version,
    seed
)

The experiment runner must:

1. Load dataset.
2. Validate dataset provenance.
3. Validate labels.
4. Validate feature version.
5. Split BEFORE fitting.
6. Fit preprocessing only on training data.
7. Train model only on training data.
8. Evaluate only on untouched test data.
9. Save model metadata.
10. Save experiment manifest.
11. Save metrics.
12. Save confusion matrix.
13. Save per-class metrics.
14. Save split information.
15. Save validity checks.

Add mandatory assertions:

- train/test session IDs do not overlap
- test rows were never used for fitting
- test set is non-empty
- required labels exist
- no duplicate session IDs
- feature dimensions match
- feature version matches model
- random seed is recorded

Update evaluate.py so that it cannot accidentally evaluate a model using an independently-created split after training.

If possible, make the API structure make this misuse difficult.

For example:

TRAINED MODEL
must contain:
- training_dataset_hash
- training_session_ids/hash
- feature_version
- split_protocol
- seed

Evaluation must verify compatibility.
