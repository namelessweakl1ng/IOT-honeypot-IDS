# Build a Complete IoT Honeypot + ELK + Machine-Learning IDS Research Platform

You are building a **real, working final-year computer science/security project**, not a mockup, tutorial, toy application, or collection of disconnected scripts.

The system is a controlled cybersecurity laboratory consisting of:

1. **Raspberry Pi 4 4GB running Raspberry Pi OS Lite**

   * Acts as the honeypot/sensor.
   * Runs lightweight Docker containers.
   * Simulates realistic IoT devices commonly targeted by attackers.
   * Performs NO heavy ML processing.
   * Collects detailed attack telemetry.
   * Sends telemetry to Computer 1.
   * Must remain easy to SSH into and configure remotely.

2. **Computer 1 running either Fedora Linux OR Windows**

   * Acts as the central security-analysis machine.
   * Must be supported on both operating systems.
   * Runs the ELK stack and ML pipeline.
   * Receives and processes telemetry from the Raspberry Pi.
   * Provides the main dashboard and analysis environment.
   * Performs feature extraction, anomaly detection, model training, evaluation, and visualization.

3. **Computer 2 running Fedora Linux**

   * Acts as the controlled attacker machine.
   * Contains reproducible attack/scenario scripts.
   * Attacks ONLY the intentionally isolated honeypot/lab environment.
   * Generates realistic attack traffic for testing the system.

4. **A router**

   * Connects all three machines.
   * The design must not depend on advanced router capabilities.
   * If useful capabilities such as VLANs, firewall APIs, port mirroring, or OpenWrt are detected, support them optionally.
   * The core system must work with an ordinary LAN router.

# 8. CONTAINER ISOLATION

Security is a first-class requirement.

Assume an attacker will eventually execute malicious commands against the honeypot.

Containers must be configured to minimize damage.

Do NOT:

```text
--privileged
```

unless absolutely unavoidable.

Do not mount:

```text
/
```

from the host.

Do not expose:

```text
/var/run/docker.sock
```

to attacker-facing containers.

Use:

```text
read-only filesystems where practical
resource limits
capability dropping
non-root execution where possible
isolated Docker networks
minimal base images
health checks
restart policies
```

Where write access is necessary, use dedicated container volumes.

The real Raspberry Pi OS must never become the attacker's shell.


### ML service unavailable

ELK ingestion and visualization must continue.

# 48. ATTACK SAFETY

The attacker tooling is for the controlled lab only.

Every attack script must:

1. Require an explicit target.
2. Prefer a configured honeypot subnet.
3. Refuse obvious non-lab targets where practical.
4. Explain that it is intended only for the user's isolated environment.
5. Never default to an internet address.
6. Never scan arbitrary internet ranges.
7. Never include credential theft or persistence against real systems.
8. Never escape the Dockerized honeypot environment.

The objective is reproducible defensive research.
