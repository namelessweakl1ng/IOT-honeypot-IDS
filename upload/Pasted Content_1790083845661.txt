============================================================
CRITICAL ISSUE #1:
THE CURRENT "HELD-OUT" EVALUATION IS INVALID
============================================================

Inspect:

model-lab/model_lab/train.py

and:

model-lab/model_lab/evaluate.py

Current behavior:

train.py loads the ENTIRE dataset and trains the model on every row.

evaluate.py later creates a session-level train/test split and evaluates the already-trained model on the test rows.

Therefore:

TRAINING DATA
    |
    +---- contains the eventual test rows
    |
    MODEL
    |
    +---- evaluated on those same rows

This is NOT a valid held-out evaluation.

The current experiment artifacts claim:

"session-level held-out evaluation"

with:

train_size = 168
test_size = 42

but the model was trained on all 210 samples.

THIS MUST BE FIXED FIRST.

Do not delete the old experiment artifacts.

Instead mark existing results as:

LEGACY_INVALID_EVALUATION

or:

INVALID_LEAKED_EVALUATION

with an explicit reason:

"The estimator was trained on the complete dataset before the reported evaluation split was applied."

The existing 1.00 F1 must NOT be presented as valid generalization evidence.

============================================================
CRITICAL ISSUE #2:
TRAIN/TEST SPLITTING MUST HAPPEN BEFORE TRAINING
============================================================

Redesign the experimental API.

The correct flow is:

DATASET
  |
  +---- TRAIN SPLIT
  |
  +---- TEST SPLIT
           |
           |
      LOCK TEST SET
           |
           v
      TRAIN MODEL
           |
           v
      EVALUATE TEST
           |
           v
      RESULTS

The test set must never be passed into model fitting.

Implement an explicit experiment runner rather than allowing:

train()
then later
evaluate()

to accidentally create an invalid protocol.

Example conceptual API:

ExperimentRunner.run(
    dataset,
    split_protocol,
    algorithm,
    seed,
)

The runner should:

1. load dataset
2. validate provenance
3. validate labels
4. validate features
5. split data
6. freeze test set
7. train model only on training data
8. evaluate only on test data
9. record exact split
10. record model
11. record metrics
12. record Git commit
13. record environment
14. mark experiment VALID or INVALID

CRITICAL ISSUE #3:
LABEL PROVENANCE / CIRCULARITY
============================================================

Inspect:

model-lab/model_lab/datasets/from_es.py

dashboard/ml/rules.py

dashboard/ml/features.py

dashboard/logstash/pipelines/beats.conf

The current architecture can contain:

raw event
    |
    v
attack.classification
    |
    v
rule engine
    |
    v
dataset label
    |
    v
ML

Meanwhile some features are themselves derived from:

attack.classification

Examples include:

contains_path_traversal
contains_command_injection
contains_default_credentials

This creates a circular or near-circular labeling problem.

A detector output cannot automatically become ground truth.

Implement separate fields:

ground_truth_label
ground_truth_source
rule_prediction
classifier_prediction
anomaly_prediction
final_prediction

Never silently map:

rule_prediction -> ground_truth_label

Ground truth sources must explicitly be:

SCENARIO_GROUND_TRUTH
ANALYST_LABELED
EXTERNAL_DATASET
SYNTHETIC

and:

RULE_ENGINE
ML_PREDICTION
ANOMALY_DETECTOR

must NOT be considered ground truth.

For uncontrolled live traffic:

ground_truth = UNKNOWN

unless independently annotated.
